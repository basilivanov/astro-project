# 📖 Методология разработки: Astro-GRACE & PCAM

Этот документ определяет стандарты разработки для проекта AstroSaaS. Все ИИ-агенты ОБЯЗАНЫ следовать этим правилам для обеспечения надежности, масштабируемости и исключения технического долга.

---

## 🏗 1. GRACE (Graph-RAG Anchored Code Engineering)
*Методология структурирования кода и данных для эффективной работы ИИ.*

### 1.1. Семантическое якорение (Anchors)
- **Суть:** Весь код разделяется на логические блоки, ограниченные парными комментариями-тегами.
- **Формат:** 
  ```python
  # #START_BLOCK_UNIQUE_ID
  код...
  # #END_BLOCK_UNIQUE_ID
  ```
- **Правило:** Правки вносятся строго внутри блоков. Имена блоков должны быть уникальными и описательными.

### 1.2. AI-Headers (Семантический каркас)
- Каждый файл начинается с заголовка, описывающего его роль в графе проекта и список доступных якорей.
- **Цель:** Позволить ИИ мгновенно "прицелиться" в нужную часть файла без полного сканирования.

### 1.3. Контрактное программирование
- Перед каждой функцией/классом в docstring прописывается "Контракт":
  - **PURPOSE:** Зачем нужен этот код.
  - **INPUT/OUTPUT:** Четкая типизация данных.
  - **CONTEXT:** Какие внешние зависимости или якоря используются.

### 1.4. Thinking Tokens (Рефлексия)
- При генерации сложной логики ИИ сначала должен вербализировать свои рассуждения в теге или поле `<thinking>`. Это повышает точность и обоснованность кода.

## 🎯 2. PCAM (Purpose-Context-Action-Measure)
*Методология постановки и выполнения задач ИИ-агентами.*

При получении задачи, агент должен разложить её на 4 составляющие:
1.  **Purpose (Цель):** Конечный бизнес-результат (например, "Клиент должен видеть расчет Сатурна").
2.  **Context (Контекст):** Какие файлы и конкретные **Якоря GRACE** будут изменены.
3.  **Action (Действие):** Пошаговый план изменений.
4.  **Measure (Мера успеха):** Как мы проверим результат (Pydantic-валидация, тесты, логи).

---

## 🪵 3. LDM (Log-Driven Model)
- Код должен генерировать логи, привязанные к именам блоков GRACE.
- При возникновении ошибки, лог должен прямо указывать на проблемный якорь (например, `Error in #BLOCK_SOLAR_CALC`).
- ИИ-агент использует эти логи для автоматической коррекции (Self-Healing).

---

## 4. Testing & Debugging (Log-Driven)
- **Минимальные тесты:** избегаем перегруза автотестами; ассерты только базовые и там, где без них нельзя.
- **Опора на логи:** проверки качества делаются через анализ логов (AI Friendly), а не через сложные assert-цепочки.
- **Диагностический прогон:** в приложении должен быть CLI/админ-триггер, который прогоняет ключевые сценарии и собирает логи + артефакты.
- **GRACE-координаты в логах:** каждый лог содержит ID блока, шаг пайплайна и ключевые идентификаторы (`client_id`, `report_id`), чтобы быстро локализовать дефект.
- **Валидация на границах:** используем Pydantic/JSON schema для контроля входов/выходов компонентов.

---

## 💎 5. Стандарты данных
- **JSON + Pydantic:** Весь обмен данными между Engine, Backend и Frontend происходит только через типизированные JSON-объекты.
- **Tailwind 4 CSS:** Стилизация фронтенда выполняется внутри блоков верстки с использованием современных CSS-переменных.

---

## 🛠 Инструкция для Агента:
1.  **Understand:** Прочитай задачу и найди нужные файлы.
2.  **Locate:** Найди якоря GRACE или создай новые, если блок отсутствует.
3.  **Plan (PCAM):** Опиши, что ты сделаешь.
4.  **Execute:** Вноси правки строго между тегами `#START_...` и `#END_...`.
5.  **Verify:** Запусти код и проверь вывод (Measure).
